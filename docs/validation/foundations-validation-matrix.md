## How to read the tables

| Field | Meaning |
| --- | --- |
| ID | `TFO` terminal-file-operations, `LAS` local-access-and-secrets, `GCM` git-change-management. `G` = guided lab, `C` = challenge, `P` = probe of a canonical safety claim (see the plan). |
| Status | Always `PLANNED` in this phase. Vocabulary: `PLANNED`, `EXECUTED`, `PASSED`, `FAILED`, `BLOCKED`, `NOT APPLICABLE`. |
| Section / objective | Canonical section and the objective (`O1`–`O5`) the case validates. |
| Linux, macOS | `Y` applicable; `Y(Dnn)` applicable with a divergence from the register; `C` conditional, needs a maintainer decision before execution; `VM` Linux disposable VM required; `N/A` not applicable (reason given). |
| Setup | `fresh` = new sandbox, nothing inherited. `after X` = same lab run, immediately following case `X`. `fixture` = purpose-built sandbox described in the case. |
| Commands | `V:` = copy the canonical fenced block(s) of that section **byte for byte**; any deviation is recorded as a deviation. Extra read-only commands are written out. `O-*` = oracle recipe from the plan. |
| Evidence | `T` transcript record, `M` mode observation, `C` content observation, `S` directory-state observation, `R` reviewer note, plus named oracles. Definitions are in the evidence template. |
| Safety | `SAFE` read-only or non-destructive; `CONTROLLED` modifies only disposable laboratory files; `HIGH-RISK` permissions, destructive cleanup, or potentially dangerous Git operations. A temporary directory never makes a command SAFE. |
| Cleanup | `CL-RUN` covered by that module's cleanup cases in the same run. `CL-SBX` sandbox teardown by the checklist (fixtures). `none` nothing to clean. |

**General verdict rules (apply to every case):** an unexpected nonzero status, a `STOP` line, an unexpected prompt, or any write outside the lab makes the case `FAILED`; it is never repaired and re-labelled as passed. A case is `BLOCKED` when its precondition or environment is unavailable (for example, the process runs as root when the module requires an ordinary user). Where the canonical text allows variable wording, only the stated assertion is checked, never message text alone.
